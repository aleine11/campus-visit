## 一、项目整体架构

```
浏览器 (Vue3 前端)
   ↓ HTTP 请求 (JSON + JWT 令牌)
Controller 控制层   ← 接收请求、参数校验、返回 Result
   ↓
Service 业务层      ← 业务逻辑（预约审核、名额扣减、RAG 编排…）
   ↓
Mapper 数据访问层   ← MyBatis-Plus 自动生成 CRUD，不用写 SQL
   ↓
MySQL 8.0          ← 8 张业务表（用户/公告/场次/预约/知识库/会话/消息）

旁路组件（AI 咨询用）：
PDF/Word 文档 → PDFBox/POI 解析 → 文本分块 → BGE 模型转向量 → Milvus 存储
访客提问 → BGE 向量化 → Milvus 检索相似片段 → 拼提示词 → 阿里百炼 qwen-plus 生成回答
```

**为什么要分层？** 每层只干一件事，改哪层不影响别层（比如以后换数据库只动 Mapper 层），答辩也好讲清楚。

## 二、模块 0 知识点详解

### 2.1 MyBatis-Plus 实体注解（Entity 怎么"翻译"数据库表）

| 注解 | 作用 | 通俗解释 |
|------|------|---------|
| `@TableName("visitor_user")` | 指定表名 | 这个类对应数据库哪张表 |
| `@TableId(type = IdType.AUTO)` | 主键 + 自增 | id 由数据库自动分配 1、2、3… |
| `@TableLogic` | 逻辑删除 | "删除"只是把 deleted 字段改成 1，数据还在库里，查询时自动过滤掉 |
| `@Version` | 乐观锁版本号 | 防止多人并发修改把数据改乱（见 2.2） |
| `@TableField(fill = FieldFill.INSERT)` | 插入时自动填充 | 插入数据时 createTime 自动填当前时间，不用手动赋值 |
| `@TableField(fill = FieldFill.INSERT_UPDATE)` | 插入和更新都填充 | updateTime 每次改动自动刷新 |

> 项目里只有 3 张表用逻辑删除：公告、场次、知识库文档（这些数据有恢复价值）。
> 用户、预约、会话、消息表不用——预约删了就是删了，符合真实业务。

### 2.2 乐观锁防超卖（本项目的核心难点之一）

**场景**：某场次只剩 1 个名额，访客 A 和 B 同一秒提交预约。

```
A 的更新：UPDATE visit_session SET used_people = used_people + 2
          WHERE id = 1 AND version = 0     ← 影响行数 1，成功，version 变 1
B 的更新：UPDATE visit_session SET used_people = used_people + 2
          WHERE id = 1 AND version = 0     ← 影响行数 0，失败！version 已经不是 0 了
```

- MyBatis-Plus 的乐观锁插件自动帮我们加 `AND version = ?` 条件
- 业务代码发现更新影响 0 行 → 回滚事务 → 提示"名额已被抢完"
- **"乐观"的含义**：不加数据库锁，先假设没冲突，提交时才发现冲突（和"悲观锁"对比：悲观锁是一上来就锁住表，别人干等）

### 2.3 统一返回格式 Result + 状态码 ResultCode

**所有接口**都返回同一个 JSON 结构，前端只用写一套处理逻辑：

```json
{
  "code": 200,          // 200 成功；4xxxx 业务失败；5xxxx 系统错误
  "message": "success", // 提示信息
  "data": { ... },      // 业务数据，失败时是 null
  "timestamp": 1693100000000
}
```

状态码采用 **4xxxx 分段**（对标 architecture.md 第六章）：

| 分段 | 含义 | 例子 |
|------|------|------|
| 200 | 成功 | - |
| 40001~40099 | 参数/业务校验失败 | 40010 用户名或密码错误 |
| 40101 | 未登录 / token 过期 | 拦截器抛出 |
| 40301 | 无权限 | 访客访问管理员接口 |
| 40401 | 资源不存在 | 预约单不存在 |
| 50000 | 系统异常 | 兜底 |

**BusinessException（业务异常）**：业务代码里随时 `throw new BusinessException(ResultCode.RESERVATION_DUPLICATE)`，不用层层 return 错误，由 **GlobalExceptionHandler（全局异常处理器）** 统一捕获并转成上面的 JSON。

### 2.4 JWT 登录鉴权（前后端分离的标准方案）

**JWT = JSON Web Token**，本质是一串自带的"加密工牌"：

```
header.payload.signature
 头部.载荷.签名
```

- **payload（载荷）** 存：userId、role（visitor/admin）、isSuper、username、过期时间
- **signature（签名）** 用服务端密钥 secret 计算，客户端拿不到 secret → **无法伪造工牌**

**完整流程**：

```
1. 登录成功 → JwtUtil.generateToken() 生成 token → 返回给前端
2. 前端把 token 存 localStorage
3. 之后每次请求在请求头带上：Authorization: Bearer <token>
4. JwtAuthInterceptor（拦截器）在每个请求进来时验签：
   ├─ 有效 → 解析出用户信息 → 存进 UserContext（ThreadLocal）→ 放行
   └─ 无效/过期 → 抛 40101 异常 → 前端跳登录页
5. 请求结束 → UserContext.clear() 清理 ThreadLocal
```

### 2.5 BCrypt 密码加密（为什么不用 MD5？）

| 对比 | MD5 | BCrypt |
|------|-----|--------|
| 速度 | 极快（反被攻击者利用） | 慢（故意的，单次约 100ms） |
| 随机盐 | 无，同密码散列相同 | 有，同密码每次散列都不同 |
| 抗撞库 | 彩虹表可破解 | 几乎不可能 |

- 注册时：`BcryptUtil.encode("明文")` → `$2a$10$xxxx...`（60 位散列）存库
- 登录时：`BcryptUtil.matches("用户输入", "库里的散列")` → true/false
- **数据库永远不存明文密码**，就算库泄露了密码也安全

### 2.6 ThreadLocal 用户上下文（UserContext）

**问题**：请求里的用户信息存在请求头 token 里，Service 层怎么拿到当前用户？

**方案**：ThreadLocal = "每个线程自己的口袋"。
- Spring MVC 一个请求 = 一个线程
- 拦截器解析 token 后 `UserContext.set(用户信息)`
- 之后 Controller / Service 任何地方 `UserContext.getUserId()` 直接拿，不用层层传参

**⚠️ 必须在请求结束 clear()**：Tomcat 用线程池复用线程，不清理的话上一个用户的身份会"串"给下一个请求——重大安全漏洞！

### 2.7 注解式权限控制（@RequiresLogin / @RequiresRole）

在 Controller 方法上加注解即可获得鉴权能力，代码零侵入：

```java
@RequiresLogin                    // 只要登录
@GetMapping("/my-reservations")
public Result<?> myReservations() { ... }

@RequiresRole("admin")            // 要管理员角色（隐含需要登录）
@PostMapping("/admin/notice/save")
public Result<?> save(@RequestBody NoticeSaveDTO dto) { ... }

@RequiresRole(value = "admin", superOnly = true)   // 只要超管
```

拦截器自动读注解决定校验方式——**方法级注解优先于类级注解**。

### 2.8 数据库设计规范（database.md 精华）

| 规范 | 说明 |
|------|------|
| 字符集 utf8mb4 | 完整 UTF-8，支持 emoji 和生僻字 |
| 引擎 InnoDB | 支持事务（预约扣名额必须事务） |
| 主键统一 `id BIGINT AUTO_INCREMENT` | 与 MyBatis-Plus `id-type: auto` 对齐 |
| 不用物理外键，只建索引 | 一致性由应用层维护，方便迁移 |
| 联合索引最左前缀 | `idx_status_publish(status, publish_time)` 支撑"查已发布+按时间排序" |
| 冗余字段换性能 | 预约表冗余 real_name/phone，消息表冗余 visitor_id，避免 JOIN |
| 时间字段 | create_time/update_time 全表必备，自动填充 |

## 四、常见报错排查表

| 报错信息（关键词） | 原因 | 解决 |
|-------------------|------|------|
| `Access denied for user 'root'` | MySQL 密码不对 | 检查 application-dev.yml 的 password |
| `Unknown database 'campus_visit'` | 没执行第①个 SQL | 执行 docs/init-database.sql |
| `Table 'xxx' doesn't exist` | 没执行建表 SQL | 执行 schema.sql |
| `Communications link failure` | MySQL 服务没启动 | 回到第 1 步启动服务 |
| `Public Key Retrieval is not allowed` | JDBC 参数缺 | 配置里已加 `allowPublicKeyRetrieval=true`，检查 URL 没被改坏 |
| `Port 8088 was already in use` | 端口被占 | 关掉占端口的程序，或改 application.yml 的 port |
| `不支持发行版本 17` / `invalid target release` | JDK 版本低于 17 | 回到第 5 步配 JDK 17 |
| `Field 'xxx' doesn't have a default value` | 少执行了某个 SQL | 三个 SQL 按顺序全执行一遍 |
| 控制台中文乱码 | IDEA 编码问题 | File → Settings → Editor → File Encodings 全部 UTF-8 |

## 六、模块 1 知识点详解（用户认证）

> 模块 1 产出：`AuthController`（4 接口）+ `AuthService/Impl`（双表登录）+ 3 个 DTO + 2 个 VO
> 12 项真实 HTTP 测试全部通过

### 6.1 DTO / VO 分层（为什么参数和返回要分成两种类？）

```
前端 JSON 请求 ──→ DTO（接收+校验）──→ Service 业务处理 ──→ VO（裁剪+组装）──→ 前端 JSON 响应
```

- **DTO（Data Transfer Object）**：接收参数的"入口守卫"，字段上贴校验注解
- **VO（View Object）**：返回数据的"出口裁剪"，**永远不把 Entity 直接返回**——Entity 里有 `password` 散列、`status`、`deleted` 等敏感/无关字段
- 答辩常问：「为什么不直接返回 Entity？」→ 泄露敏感字段 + 前后端耦合（表结构一改接口就崩）

### 6.2 Bean Validation 参数校验（注解即规则）

| 注解 | 作用 | 本项目用例 |
|------|------|-----------|
| `@NotBlank` | 非 null 且非纯空格 | 用户名、密码 |
| `@Pattern(正则)` | 正则匹配格式 | 用户名 `^[a-zA-Z0-9_]{4,20}$`、手机号 `^1[3-9]\d{9}$`、密码 `^(?=.*[a-zA-Z])(?=.*\d).{6,20}$` |
| `@Size(min,max)` | 长度范围 | 真实姓名 2~10 字 |

执行链路：`Controller 参数加 @Valid` → 方法进门前 Spring 触发校验 → 失败抛 `MethodArgumentNotValidException` → 全局异常处理器转 **40001**。
密码正则里的 `(?=.*[a-zA-Z])(?=.*\d)` 是**先行断言**：分别检查"含字母"和"含数字"两个条件，但不断言具体位置。

### 6.3 双表统一登录策略（本模块最核心设计）

```
POST /api/auth/login
   │
   ├─ 1. 查 visitor_user
   │      ├─ 用户名不存在 ──→ 去 2
   │      ├─ 密码错 ──→ 40010（不再查管理员表，避免无用功）
   │      ├─ 密码对 + status=1 ──→ 40012 冻结
   │      └─ 密码对 + status=0 ──→ 签发 visitor token ✅
   │
   └─ 2. 查 admin_user
          ├─ 不存在或密码错 ──→ 40010
          └─ 匹配 ──→ 签发 admin token（带 isSuper）✅
```

三个安全细节（答辩加分点）：
1. **用户名不存在和密码错误返回同一个 40010 提示**——防止攻击者靠提示差异探测哪些用户名已注册
2. **注册时双表查重**——如果允许访客注册与管理员相同的用户名，登录时访客表先命中，管理员账号会被"遮蔽"永远登不上
3. **先验密码再查冻结状态**——避免暴露"该账号存在且已被冻结"给密码错误的人

### 6.4 JWT 登录全流程（模块 0 的工具在模块 1 串成线）

```
登录成功 → JwtUtil.generateToken(userId, role, isSuper, username)
        → 前端保存 token
        → 之后每次请求带 Authorization: Bearer <token>
        → 拦截器 verify + 解析 → UserContext.set()
        → Controller/Service 用 UserContext.get() 取当前人
        → 请求结束 afterCompletion → UserContext.clear()
```

关键理解：**JWT 是无状态的**——服务端不存 session，用户身份全部写在 token 里、由签名防篡改。副作用：改密后旧 token 依然有效（无法单方面作废），生产环境要配 Redis 黑名单，毕设可接受。

### 6.5 面向接口编程（AuthService 接口 + Impl 实现）

Controller 只依赖 `AuthService` 接口，不关心实现细节。好处：换实现/加逻辑（如登录验证码）Controller 零改动；配合 Spring 依赖注入（`@Resource`），测试时可以注入假实现。
`@Resource` vs `@Autowired`：两者都能注入，`@Resource` 是 Java 标准注解按名称找，`@Autowired` 是 Spring 的按类型找。项目统一用 `@Resource`。

### 6.6 LambdaQueryWrapper（类型安全的 where 条件）

```java
new LambdaQueryWrapper<VisitorUser>().eq(VisitorUser::getUsername, dto.getUsername())
// 等价 SQL：SELECT * FROM visitor_user WHERE username = ?
```

比手写 SQL 字符串的好处：`VisitorUser::getUsername` 是方法引用，字段改名时编译器直接报错，拼错列名在编译期就能发现（运行期才发现的字符串 SQL 做不到）。

## 七、答辩问答锦囊（持续追加）

> 开发过程中预判老师可能提问的问题，提前准备标准答案。每完成一个模块追加。

### Q1：「你的系统可维护性如何？后期修改困难吗？」

**标准回答**：

> "系统采用分层架构 + 模块化设计，业务层按功能垂直拆分，模块间通过 Service 接口通信、互不侵入；公共能力（鉴权、异常处理、统一返回格式）下沉到公共组件层。新增业务模块只需增加独立文件，不修改已有代码，符合开闭原则。"

**展开支撑点**（老师追问时用）：

1. **分层隔离**：Controller（接口）→ Service（业务）→ Mapper（数据），每层职责单一，改一层不影响其他层
2. **模块垂直拆分**：公告、场次、预约等每个业务模块拥有自己独立的 Controller/Service/DTO/VO 文件，互不掺杂
3. **公共组件复用**：Result 统一返回、全局异常处理、JWT 拦截器做成通用底座，业务代码只加注解就能获得鉴权能力
4. **开闭原则**：对扩展开放、对修改关闭——新增功能 = 新增文件，不动老代码，从源头避免"改一处崩一片"

**改动难度分档**（如果老师继续追问"具体改起来呢？"）：

| 分档 | 修改类型 | 难度 |
|------|---------|------|
| 🟢 容易（80% 需求） | 单模块逻辑调整、加字段、加新模块、改前端样式 | ⭐~⭐⭐ |
| 🟡 中等 | 跨模块联动（如预约成功发通知）、表结构大改 | ⭐⭐⭐ |

## 八、模块 2&3 知识点精要（公告 / 场次）

### 8.1 逻辑删除的"隐形过滤"（@TableLogic）
实体标 `@TableLogic` 后，MyBatis-Plus 全自动：
- 查询自动追加 `WHERE deleted=0`（业务代码一行不用写）
- `deleteById(id)` 实际执行 `UPDATE SET deleted=1`（不是物理 DELETE）

好处：删错能恢复、审计友好、业务代码干净。前台删除后"立即不可见"就是这么实现的。

### 8.2 分页插件（物理分页）
```java
Page<T> p = new Page<>(页码, 每页条数);
mapper.selectPage(p, wrapper);   // 拦截器自动拼 LIMIT
p.getTotal();                    // 总条数（前端分页控件用）
```
"物理分页"= 数据库层面只查本页 10 条，不是查全部再内存截取（那是逻辑分页，数据量大时卡死）。

### 8.3 动态查询条件（if 的优雅写法）
```java
wrapper.like(keyword != null, Notice::getTitle, keyword)
```
第一个参数是"开关"：false 时这个条件根本不拼进 SQL。一行替代传统 XML 里一大坨 `<if test="...">`。

### 8.4 状态机流转（防脏数据）
发布/下架/上架前必须先校验当前状态，非法流转报 40022：
```
公告：草稿(0) ⇄ 已发布(1)
场次：开放(0) ⇄ 下架(1)
```
没有状态机 → 同一个"发布"按钮连点两次 → 重复写入发布时间 → 数据错乱。**答辩高频考点。**

### 8.5 日期校验注解（@FutureOrPresent）
```java
@FutureOrPresent(message = "参观日期不能早于今天")
private LocalDate visitDate;
```
LocalDate 无时分秒，"present" 即今天 → 效果 = 今天及以后合法。过去日期在进 Service 前就被拦截（40001）。这是"禁止创建过去时间场次"约束的第一层防线。

### 8.6 场次模块的三大业务约束（对应测试重点清单第 1 条）
| 约束 | 拦截位置 | 错误码 |
|------|---------|--------|
| 禁止创建过去场次 | DTO 注解 + Service 二次防御 | 40001 |
| 缩容保护（maxPeople 不得 < usedPeople） | Service | 40022 |
| 删除保护（usedPeople>0 禁删） | Service | 40022 |

删除保护的本质是**引用完整性**：预约表引用了场次，删场次会让预约变成"孤儿数据"（查不到场次信息）。所以有预约只能"下架"（停止预约但数据保留），不能删。

### 8.7 剩余名额的"计算字段"模式
`remaining = maxPeople - usedPeople` 在 VO 里现算，不存数据库——避免"存了又忘更新"的不一致问题。**凡是能从别的字段推导出来的值，都不要存表。**

### 8.8 乐观锁登场预告
场次实体的 `@Version` 在本模块只是"顺带生效"（编辑时自动追加 version 条件）。真正唱主角在模块 4：访客抢名额时 `UPDATE ... SET used=used+N WHERE id=? AND version=?`，影响行数=0 就是被人抢了 → 提示"名额不足"。两个请求同时改同一行，数据库层面保证一先一后，这就是并发安全。

### 8.9 模块 2&3 实测记录（复习用证据）
- 模块 2 公告：15 项全过（草稿前台不可见 40401、重复发布 40022、逻辑删除后 total 减 1、无 token 40101）
- 模块 3 场次：22 项全过（过去日期 40001、缩容/删除保护 40022、上下架状态机双向拦截、下架场次前台隐藏、remaining 动态计算 80=100-20）
